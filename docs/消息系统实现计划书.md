# 消息系统（be-message-service）实现计划书

> 基于 `be-message-service` 当前代码现状整理，把剩余工作拆成「分阶段、分模块」的推进路线。
> 目标：四大模块（系统通知 / 事件提醒 / 私信 / 消息设置）可上线、数据正确、推送闭环、可运维。
> 技术栈：FastAPI（REST）+ FastStream（RabbitMQ 消费）+ SQLModel + Alembic + APScheduler；
> 存储只用 MySQL（**不使用 Redis**），私信正文按月分库 + 库内 100 表。

**关键设计已定型**：通知读扩散（游标去重）、事件写扩散（聚合索引 + `dedup_key` 幂等）、私信写扩散（会话/索引主库 + 正文异步分片 + 死信补偿）。

**站内信 vs 第三方推送（重要修正）**：系统通知 / 事件提醒 / 私信属于**站内信**，送达完全由数据库写路径保证（用户经 `/pull` `/list` `/messages` `msg_feed` 轮询感知），**不经由任何第三方推送渠道**。第三方推送（PushMe / PushPlus / SMTP 等）是**独立于站内信**的能力，仅用于「站外提醒」类内容，由 `/api/v1/message/push` 投递到 `message.push` 队列单独处理。早期把站内信也转发到第三方渠道的设计是混淆，现已拆分干净。

**活跃度与推送策略已解耦**：`UserActivity` 的活跃度判定**仅用于前端轮询节奏**（判断是否在线），与消息送达无关。已彻底移除「活跃→实时推第三方 / 非活跃→批量聚合并推第三方」的相关代码与字段：
- 枚举 `PushStrategyEnum`（REALTIME/BATCH/SKIPPED）、`ActivityService.decide_strategy`；
- `ActivityService.incr_pending` / `fetch_pending_users` / `reset_pending` 及 `UserActivity.pending_push_count` / `last_batch_push_at`；
- `EventMessage.push_strategy` / `pushed` 字段、`EventReportResp.push_strategy`；
- 定时任务 `batch_push_job`、配置项 `inactive_push_interval_seconds` / `batch_push_user_limit`。
> 注：上述字段在初始 Alembic 迁移（`20260803_1154-*`）中已建表，清理后需再生成一次 `alembic revision --autogenerate` 以 DROP 这些废弃列，保持库表与模型一致。

## 二、分阶段实施路线

### Phase A — 数据层收尾（阻塞上线，最先做）

> 问题根因：模型里 `StrEnum` 字段用 `Field(max_length=16)`，SQLModel 默认落成**原生 ENUM 且存成员名**（`LIKE` 而非 `like`）；自动生成的迁移继承了这个问题。
> 后果：① 库里字面量与接口层 `like` 对不上，查询/过滤全错；② 后续加枚举值要 DDL 改表。

- [x] **A1. 模型枚举列改用 `str_enum_type()`**
  - `app/models/db/notify.py`：`target_type` / `level` / `status` → `Field(sa_type=str_enum_type(NotifyTargetTypeEnum/NotifyLevelEnum/NotifyStatusEnum))`
  - `app/models/db/event.py`：`event_type` / `source_type` → `Field(sa_type=str_enum_type(EventTypeEnum/SourceTypeEnum))`
  - `app/models/db/dm.py`：`session_type`→`str_enum_type(DmSessionTypeEnum)`、`msg_type`→`str_enum_type(DmMsgTypeEnum)`、`relation`→`str_enum_type(DmRelationEnum)`
  - 注：`DmMsgStatusEnum`/`DmSessionTypeEnum` 是 `IntEnum`，保持整数列 **不要** 改；`dm.py` 已 `import` `str_enum_type`，当前未使用，需补上实际调用。
- [x] **A2. 重新生成 Alembic 初始迁移**
  - 删除并重建初始迁移：`uv run alembic revision --autogenerate -m "init_message_system_schema"`
  - 校验生成的列类型为 `VARCHAR(n)`（存值），**不再出现** `sa.Enum(..., name=...)`；`AutoString` 长度统一。
- [x] **A3. 对运行中的 MySQL 执行并验证**
  - 目标库 `BiliMessageDB`（本地 `127.0.0.1:10000`，可走 `MYSQL_MESSAGE_URL`）
  - `uv run alembic upgrade head` → 确认 10 张表落库、枚举列为 VARCHAR、抽样值正确（`like`/`text`/`single`/`normal`）。
- [x] **A4. 完善 `.env.example`**
  - 补充 `MYSQL_MESSAGE_URL=mysql+aiomysql://root:${MYSQL_PASSWORD}@mysql:3306/BiliMessageDB?charset=utf8mb4` 及说明（与 `docker-compose.yml` 保持一致）。

**出口标准**：`uv run python -c "import app.main"` 通过；迁移在干净库上 `upgrade head` 可复现；枚举列存值一致。

## 三、风险与缺口

1. **枚举值不一致（最高优先级，Phase A）**：迁移现有原生 ENUM 存成员名，必须先改模型重生成迁移，否则线上数据错乱。
2. **受众可见性兜底**：`resolve_target_mids` 按 `recv_notify=True` 推全量，精确可见性在 `/pull` 时由 `_target_condition` 再过滤；自定义/角色/等级/VIP 投放的命中逻辑需在 B1 实测确认。
3. **第三方推送渠道弱依赖（仅站外提醒）**：PushMe/PushPlus 等仅由 `/api/v1/message/push` 用于「站外提醒」类内容，与站内信（系统通知/事件提醒/私信）完全解耦；端点故障仅告警不阻断，不影响站内信送达。
4. **分片无 Alembic 管理**：月度内容库由 `sharding` 懒创建，`downgrade` 不回滚分片，需靠 `prewarm_shard_job` + 手动运维。
