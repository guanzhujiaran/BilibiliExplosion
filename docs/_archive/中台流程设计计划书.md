# RPA 中台流程设计计划书

> 基于现有 RPA-Browser 后端能力梳理，设计中台（治理能力层）的流程、闭环与演进路线。
> 中台定位：位于「终端用户 / 社区」与「RPA 执行引擎」之间的治理能力层，负责
> **权限收敛、审批闭环、资源治理、审计风控、社区治理、系统运维**。

---

## 一、现状能力盘点（已对照后端代码确认）

| 模块 | 已有端点 | 说明 |
| --- | --- | --- |
| 身份/权限 | `/role/me`、`/role/grant`、`/role/revoke`、`/role/list` | root 来自 `TUserInfo.role`；admin 来自 `rpa_admin` 表（root 授予，持久化）；权限为 JSON 列表，`*`=全部 |
| 审批 | `/approval/submit`、`/approval/list`、`/approval/review` | **仅记录，未与执行/发布联动**；状态 `pending/approved/rejected` |
| 标签 | `/tag/create/update/delete/list/attach/detach/list-by-target` | 关联 `action/workflow/plugin` |
| 官方认证 | `/certification/certify/revoke/list` | 标记 `verified` |
| 审计 | `/action-logs/list/get/by-execution/delete/clear/stats` | 含 mid/action_id/workflow_id/status/params/result/error |
| 社区 | `/community/.../list/fork/like/report`、`/community/report/update` | **举报无管理员审核端点** |
| 运维 | `/sessions/all`、`/config/browser-session`（get/post） | 配置仅内存，重启丢失 |

**关键缺口**
1. 审批流是「记录型」，执行/发布接口不校验审批单 → 无强制管控。
2. 社区举报有提交无审核闭环。
3. 权限粒度粗（`*` 全有或全无），无按资源类型的细分。
4. 管理员自身操作（授 admin / 认证 / 审核）无结构化审计表。
5. 操作日志未关联审批单 ID，无法回溯「某次执行是否经过审批」。
6. 运行时配置不持久化。

## 二、中台核心流程设计

### 流程 1：身份与权限开通流程
```
root(TUserInfo.role=root)
   │  role/grant(mid, note)
   ▼
rpa_admin 表写入(mid, role=admin, granted_by, permissions)
   │
   ▼
普通用户登录 → role/me → {is_root, is_admin, permissions, mid}
   │
   ├─ 前端：导航显隐 + 路由守卫(requiresAdmin) 按 is_admin||is_root 判断
   └─ 后端：require_admin 依赖注入强制校验
```
- **增强建议**：`permissions` 从 `["*"]` 细化为 `["approval:review","tag:*","cert:*","admin:grant"]` 等，按资源类型/动作拆分；`role/grant` 写入独立审计记录。

### 流程 2：操作审批流程（核心，当前为缺口，需闭环）
```
普通用户
   │  approval/submit(resource_type, resource_id, action=publish|execute, title, desc)
   ▼
ApprovalRequest(status=pending, submitter_mid)
   │
   ├─【通知】推送管理员「待审待办」
   ▼
管理员/root
   │  approval/review(approval_id, status=approved|rejected, review_note)
   ▼
ApprovalRequest(status=已决, reviewer_mid, reviewed_at)
   │
   ├─【通知】推送提交人「审核结果」
   ▼
执行/发布接口强制校验：
   if action 需要审批:
       must 存在 approved 且未过期的审批单(关联 resource_type+resource_id+action)
       else → 拒绝并提示「请先提交审批」
```
- **状态机**：`pending → approved | rejected`（可选扩展 `revoked / expired`）。
- **强制联动落点**：`actions_execute` / `workflows_execute` / 社区 `publish` 增加 `approval_id` 依赖校验（后端 `require_approval` 依赖）。
- **前端落点**：审批 Tab（全部/我的申请、状态筛选、审核弹窗写 review_note）、提交发布前拦截提示「需先审批」、待办角标。

### 流程 3：资源治理流程（标签 + 官方认证）
```
标签治理：
  管理员 tag/create(name,color) → rpa_tag
  管理员/用户 tag/attach(tag_id, target_type, target_id) → rpa_tag_rel(唯一约束)
  list-by-target 反查某资源的所有标签

官方认证治理：
  管理员 certification/certify(target_type, target_id, note) → rpa_certification(verified)
  certification/revoke → 删除并留痕
```
- **增强建议**：标签分层（类目标签 / 官方标签 / 用户自定义）；认证与标签在资源卡片联动展示；认证撤销写入审计。

### 流程 4：审计与风控流程
```
每次执行自动落 ActionLogRecord（mid, action_id, workflow_id, browser_id, session_id,
                                 status, params, result_data, error_message, execution_time）
   │
   ├─ 用户/管理员 action-logs/list 按条件检索
   ├─ action-logs/by-execution 拉「一次执行的完整链路」（含插件/嵌套 depth）
   ├─ action-logs/stats 统计（成功率/失败率/耗时）
   └─ action-logs/clear 按条件清空（建议加二次确认 + 操作审计）
```
- **风控增强**：失败率/超时阈值告警；批量高危操作识别；**日志关联 `approval_id`** 实现「执行↔审批」双向回溯；新增 `admin_audit_log` 表记录所有管理员操作。

### 流程 5：社区治理流程（当前缺口）
```
用户 community/.../report(target_type, target_id, reason)
   │
   ▼（现状断点：无审核端点）
管理员 community/report/review(report_id, decision=ignore|warn|takedown, note)  ← 需新增
   │
   ├─ ignore：标记已处理，通知举报人
   ├─ warn：对被举报人发警告
   └─ takedown：下架资源 + 通知双方
```
- **后端缺口**：需新增 `admin/report/list`、`admin/report/review` 端点与举报状态机。

### 流程 6：系统运维流程
```
管理员 sessions/all → 监控活跃浏览器会话(mid, browser_id, is_manual_mode, priority)
管理员 config/browser-session(get/post) → 调整自动清理/空闲时长（⚠ 仅内存）
```
- **增强建议**：运行时配置落 `.env`/持久化存储；配置变更写审计；会话异常（僵尸/卡死）主动告警。

## 四、后端能力缺口与演进路线

### P0（必须先做，打通闭环）
1. **审批强制联动**：`execute/publish` 增加 `require_approval` 依赖，校验 approved 且未过期审批单。
2. **审批通知**：提交→推管理员；审核→推提交人（复用 `utils.my_send_notify`）。
3. **社区举报审核端点**：`admin/report/list`、`admin/report/review` + 举报状态机。

### P1（治理加固）
4. **细粒度权限**：`permissions` 按 `资源:动作` 拆分，`require_admin` 扩展为 `require_permission`。
5. **管理员操作审计表** `admin_audit_log`：grant/revoke/certify/review 全留痕。
6. **日志关联审批单**：`ActionLogRecord` 增加 `approval_id` 字段，实现双向回溯。

### P2（智能化/可观测）
7. **风控指标**：失败率/超时告警、批量高危识别。
8. **运行时配置持久化**：config 变更落库/`.env`，重启不丢。
9. **标签分层体系**：类目/官方/用户自定义，支持资源卡片联动。

---

## 五、里程碑

- **M1（P0）**：审批闭环 + 通知 + 举报审核 → 中台具备真正管控力。
- **M2（P1）**：细粒度权限 + 审计表 + 日志关联审批 → 权责清晰、可追溯。
- **M3（P2）**：风控看板 + 配置持久化 + 标签分层 → 可观测、可运营。
