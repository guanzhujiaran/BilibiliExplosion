# 消息系统（be-message-service）实现计划书

> 基于 `be-message-service` 当前代码现状整理，把剩余工作拆成「分阶段、分模块」的推进路线。
> 目标：四大模块（系统通知 / 事件提醒 / 私信 / 消息设置）可上线、数据正确、推送闭环、可运维。
> 技术栈：FastAPI（REST）+ FastStream（RabbitMQ 消费）+ SQLModel + Alembic + APScheduler；
> 存储只用 MySQL（**不使用 Redis**），私信正文按月分库 + 库内 100 表。

### Phase F — 推送模块 RPC 化（be-message 作为 RPC 服务端）

> 目标：把「站外推送」能力抽象成 RabbitMQ RPC，be-message 作为唯一服务端，
> 其它系统（be-gateway / RPA-Browser / be-bilibili-crawler 等）经 `message_exchange`
> 按 `routing_key = message.push.rpc.<method>` 同步调用，不再依赖 HTTP 网关转发与
> 请求头注入的 `x-bili-*` 用户信息。契约模型统一下沉 `bili_common.models.push_rpc`。
>
> 与已有 `message.pptr.rpc.*` 模式对齐：客户端用 direct reply-to（`amq.rabbitmq.reply-to`）
> 收取响应；服务端返回 `StandardResponse{code, msg, data}`；异常在 RPC 边界翻译成
> `error_response` 回包（不静默、不吞错）。
>
> 推送 RPC 与 HTTP `/api/v1/message/push` 并存：HTTP 面向「终端用户 / 浏览器侧」，
> RPC 面向「服务端系统」，二者都落到同一套 `PushMessageService` 执行体。

- [x] **F1. 公共契约下沉 bili-common**

    - `PushRpcMethodName(StrEnum)`：`PUSH_MESSAGE`（投递队列，异步）/ `SEND_PUSH_NOW`（立即发送，同步）；

    - 契约映射 `PUSH_RPC_CONTRACT`。

### Phase H — 推送 MQ 公共发布函数下沉 bili-common（fire-and-forget）

> 背景：站外推送目前有两条调用链——HTTP `POST /api/v1/message/push`（投递到
> `message.push` 队列，异步）与 RPC `message.push.rpc.*`（同步等返回）。但各系统
> （RPA-Browser / be-gateway / be-bilibili-crawler）若只想「把推送请求丢进队列、
> 不需要管返回」，目前只能各自复制一份 MQ 发布逻辑（RPA-Browser 的
> `app/services/message/message_pub.py` 即为此）。本次把该「消息队列推送方式」
> 泛化为 bili-common 公共函数，供所有系统一行调用。
>
> 定位：与 RPC（等返回）互补——本方式是 **fire-and-forget**：函数把
> `PushMessagePayload` 发布到 `message_exchange` 的 `message.push` 队列即返回，
> 不等待 be-message 消费与第三方渠道结果。队列绑定由 be-message-service 维护，
> 公共库只发布不声明队列，避免重复绑定截获 pptr RPC 请求。

- [x] **H1. bili-common 新增推送 MQ 公共发布函数**
  - 新增 `bili_common/core/message_pub.py`（放在 `core/` 下与 `browser.py` 并列）：
    - `publish_push_message(title, content, push_type="text", config=None, amqp_url=None)`：
      构造 `PushMessagePayload`（config 兼容 `PushChannelConfig` 或 `dict`），发布到
      `message_exchange`（TOPIC / durable）的 `routing_key="message.push"`；
    - 懒连接：首次调用建立 `RabbitBroker(amqp_url)` 连接，之后复用（按 amqp_url 缓存）；
      `amqp_url` 由调用方传入（不依赖任何服务的 settings），缺省从环境变量
      `RABBITMQ_URL` 读取，再缺省回退本地默认；
    - 失败不静默：发布异常记录日志并上抛（与「不静默、不吞错」约定一致），
      但函数**不等待**任何返回（fire-and-forget 的「不等返回」指不等待消费端处理结果）；
    - 依赖边界：本模块依赖 faststream（与 `rpc/client.py` 一致为**按需子模块**，
      不进入 `core/__init__.py` 顶层导出），调用方环境需具备 faststream。

      （评论树关系：根 / 触发者评论 / 被回复评论）；
    - `root_reply_content` / `source_content` / `target_reply_content`
      （根 / 触发者 / 被回复评论正文，通知的核心内容）；
    - `like_state`（接收者对触发者评论的点赞态：0无 / 1赞 / 2踩）。
- [ ] **L2. list_msgfeed 读取时实时补全**（`app/services/event.py`）
  - 收集本页全部 `biz_id`（触发评论 rpid），一次 `WHERE rpid IN (...)` 查 `CommentIndex`
    拿 `oid / root / parent`；再收集 `root + parent` 评论 id 集合一次查 `CommentContent`
    拿正文；一次查 `CommentAction`（`rpid IN biz_ids AND mid=接收者`）拿点赞态；
    一次查 `UserFollow`（`mid=接收者 AND target_mid IN 触发者集 AND status=following`）
    拿关注态；
  - SQL 次数保持常量（与页大小无关）：分组 1 + 明细 1 + 评论索引 1 + 正文 1 + 互动 1
    + 关注 1，共 6 次，禁止在循环体发查询；
  - 语义映射：`subject_id=index.oid`（兜底 `source_id`）、`source_id=biz_id`、
    `target_id=index.parent`（parent=0 时=root）、`root_reply_content=按 root 查正文`、
    `source_content=按 biz_id 查正文`、`target_reply_content=按 target 查正文`
    （被回复的是楼中楼评论才取值；回复根评论时由 root 正文承载，保持与 B 站一致）；
  - 兜底：非 REPLY 类型或评论已删除（查不到索引）时评论关系字段回退默认值，不阻断列表返回。
- [ ] **L3. 前端对齐**（Vue 侧 msgfeed 渲染）
  - 回复条目展示「回复了你的评论」+ 楼中楼上下文（root / source / target 正文）；
  - 快捷互动按钮按 `hide_reply_button` / `hide_like_button` / `like_state` 渲染。
- [ ] **L4. 验证**
  - seed 一条回复事件 → `/event/msgfeed` 出参包含 subject_id / root_id / source_id /
    target_id / 三段正文 / native_uri / business_id / like_state / follow / mid_link /
    is_multi / reply_time，字段与 B 站样例对齐；
  - 删除触发评论后再拉取：评论关系字段安全回退，接口不报错。

### Phase M — 动态审核总统计（2.3x.0）

> 背景：管理端审核后台（`/api/v1/moment/audit`）目前只有列表 / 通过 / 驳回 / 流水 / 详情，
> 缺少「全局概览」——管理员无法一眼看到各动态类型（WORD / FORWARD）的存量分布、
> 以及各审核状态（auditing / normal / rejected / hidden）的占比。
>
> 目标：新增一个轻量统计接口，按 `dynType` + `auditStatus` 二维分组聚合 `TMoment`，
> 返回「每个类型的各状态计数」与「全局各状态汇总」。

- [ ] **M1. 统计服务方法**（`app/services/moment_audit.py` `MomentAuditService.statistics`）
  - 单条 `SELECT dynType, auditStatus, COUNT(*) ... GROUP BY dynType, auditStatus`，
    全程一次聚合，禁止循环发 COUNT；
  - 组装为「按类型明细（各状态计数 + 类型合计）」+「全局按状态汇总」+「总数」；
  - 枚举值（MomentTypeEnum / MomentAuditStatusEnum）落库为 INT / VARCHAR，
    读取时统一转 `.name` / `.value` 字符串出参。
- [ ] **M2. 响应模型**（`app/models/schemas/moment.py`）
  - `MomentAuditTypeStat`：`dynType` + `auditing/normal/rejected/hidden/total`；
  - `MomentAuditStatisticsResp`：`byType: list[MomentAuditTypeStat]` +
    `byStatus: dict[str,int]`（全局各状态汇总）+ `total: int`。
- [ ] **M3. 接口**（`app/api/moment_audit.py`）
  - `GET /api/v1/moment/audit/statistics`，`role=root`，返回 `StandardResponse[MomentAuditStatisticsResp]`。
- [ ] **M4. 验证**
  - 灌数后调用该接口，确认 byType / byStatus / total 与 `SELECT COUNT(*)` 一致。

## 三、风险与缺口

1. **枚举值不一致（最高优先级，Phase A）**：迁移现有原生 ENUM 存成员名，必须先改模型重生成迁移，否则线上数据错乱。
2. **受众可见性兜底**：`resolve_target_mids` 按 `recv_notify=True` 推全量，精确可见性在 `/pull` 时由 `_target_condition` 再过滤；自定义/角色/等级/VIP 投放的命中逻辑需在 B1 实测确认。
3. **第三方推送渠道弱依赖（仅站外提醒）**：PushMe/PushPlus 等仅由 `/api/v1/message/push` 用于「站外提醒」类内容，与站内信（系统通知/事件提醒/私信）完全解耦；端点故障仅告警不阻断，不影响站内信送达。
4. **分片无 Alembic 管理**：月度内容库由 `sharding` 懒创建，`downgrade` 不回滚分片，需靠 `prewarm_shard_job` + 手动运维。
