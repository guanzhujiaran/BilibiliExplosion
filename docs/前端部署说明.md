# 前端部署说明（Nuxt SSG：`nuxt generate`）

> 已从 Vike + Playwright 预渲染迁移到 **Nuxt 4 + `nuxt generate`**（纯静态产物，部署仍是 nginx 静态托管）。

## 1. 产物

`npm run build` 完成后的**可部署目录只有一个**：`dist/client/`

```
dist/client/
  index.html                        # 首页（服务端渲染 + 数据）
  app/lot-data/bili-data/official/index.html   # 每个收录 URL 一个 HTML
  app/.../_payload.json             # Nuxt 的数据负载（客户端 hydration 复用，无接口重放）
  _nuxt/…                           # JS / CSS（带 hash）
  favicon.ico  robots.txt  sitemap.xml  og-image.png  Ads.txt …
```

> `dist/server/` 是 Nitro 的中间产物，**不需要上传**。
> 典型体积：**约 6.6MB / 260 个文件**（迁移前是 589MB / 4665 个文件）。

### ⚠️ `action-icons/` 需要单独同步

`action-icons/`（43 个系列 / 4087 张图 / 约 581MB）**不在产物里**，它放在**项目根目录**，不是 `public/`：

- 原因：静态目录里 4000+ 个文件会让每次构建都去复制/清理它们，产物从 6.6MB 膨胀到 589MB、构建明显变慢。它本质是「不随代码发布变化」的数据；
- 部署时同步到站点根的 `action-icons/` 即可（RPA 图标页按 `/action-icons/…` 直接引用）：
  ```bash
  rsync -avz --exclude 'action-icons' dist/client/ user@server:/你的站点根/
  rsync -avz action-icons/ user@server:/你的站点根/action-icons/
  ```
  素材没变化时第二条可以跳过。
- 本地开发无需处理：`nuxt.config.ts` 在非生产模式会把该目录挂成静态目录。

## 2. 前置条件

| 场景 | 要求 |
| --- | --- |
| 构建机 | Node 20+（本项目实测 Node 26）；能访问三个后端的 `openapi.json`（`23333` / `28000` / `18739`，hey-api 生成 SDK 用）；**能访问生产接口**（预渲染时服务端要真实取数） |
| 浏览器 | **不再需要** Playwright / chromium（Nuxt 在 Node 里完成 SSR，不再用无头浏览器抓 DOM） |
| 服务器 | 什么都不需要，纯静态托管 |

## 3. 构建 + 部署

```bash
cd Vue3FrontEndDemoExercise

# ① 构建（务必指向生产接口，否则会把本地库数据写进产物）
PRERENDER_API_TARGET=https://serena.dynv6.net npm run build

# ② 校验产物
ls dist/client/index.html dist/client/sitemap.xml
grep -c "筛选结果" dist/client/app/lot-data/bili-data/official/index.html   # 应有真实条数
grep -c "localhost:4180" dist/client/index.html                             # 必须为 0

# ③ 上传（--delete 清掉上一版带 hash 的旧文件）
rsync -avz --delete --exclude 'action-icons' dist/client/ user@server:/你的站点根/
rsync -avz action-icons/ user@server:/你的站点根/action-icons/     # 素材有更新时才需要
```

构建脚本里包含几步自动化（见 `package.json`）：

1. `node scripts/prepare-build.mjs`：把上一版 `dist` 与 Nuxt 构建缓存**归档到系统临时目录**
   （不用 `rm -rf`：某些受管环境对批量删除有拦截，会直接打断构建；归档顺带保留可回滚的上一版）；
2. `nuxt generate`：SSR 渲染 10 个收录页 + 生成 `_payload.json`；
3. `node scripts/gen-sitemap.mjs`：生成 `dist/client/sitemap.xml`（清单与 `src/config/seo_routes.ts` 同源）。

## 4. nginx 要点

`/api` 反代到 be-gateway 的部分保持不变。静态文件查找规则：

```nginx
location / {
    # 精确文件 → <path>/index.html → SPA fallback
    try_files $uri $uri/index.html /index.html;
}
```

- **不要**写成 `try_files $uri $uri/ /index.html`：`$uri/` 会 301 到带尾斜杠的 URL，而页面的 `canonical` 是**不带**尾斜杠的，会形成两套 URL；
- `*.html` 不缓存或极短缓存，`_nuxt/`（文件名带 hash）可长缓存 `max-age=31536000, immutable`。

## 6. 常见坑（迁移时实际踩过）

1. **预渲染必须串行**：每个列表页在 SSR 阶段都要真实请求后端，并发抓取会被网关限流（实测 4 页并发时全部取数失败），
   `nitro.prerender.concurrency = 1` 是刻意设置，别改回默认。
2. **SSR 取数必须用绝对地址**：Node 里没有「同源」，相对路径会直接抛错。目标由
   `nitro.replace` 注入 `__SSR_API_TARGET__`（构建期取自 `PRERENDER_API_TARGET`）。
   注意：`vite.define` / `import.meta.env` 在 Nitro 的 server bundle 里**不生效**，只能走 `nitro.replace`。
3. **`VITE_*` 在服务端读不到**：Vite 默认只注入客户端，`nuxt.config.ts` 用 `vite.define` 把 `import.meta.env.VITE_*` 一并注入了服务端，所以代码里既有的写法不用改。
4. **首屏数据必须在 setup 阶段取**：原来放在 `onMounted` 的请求在 SSR 时不会执行，预渲染出的 HTML 会是「筛选结果 0 / 加载中」。
   列表页已改为 `await useAsyncData(...)`（配 `app.vue` 的 `<Suspense>`），数据同时进入 payload 供客户端 hydration 复用。
5. **`action-icons` 别放回 `public/`**：会让产物变成 589MB，并让构建反复复制/清理 4000+ 文件。
6. **持久化插件只能客户端注册**：`pinia-plugin-persistedstate` 在 SSR 会访问 `window`，见 `src/plugins/pinia-persist.client.ts`。
7. **模块顶层不要调用 `isMobileDevice()`**：它读 `navigator.userAgent`，SSR 会崩（`src/utils/Browser/useDeviceDetect.ts` 已加守卫，
   但 `BiliJump.ts` / `lotteryNormalization.ts` 仍在模块顶层调用一次，仅因守卫返回「桌面端」才不报错）。

## 7. SEO 落地情况

| 能力 | 状态 |
| --- | --- |
| title / description / canonical / OG / Twitter / robots | ✅ 按路由输出；列表页 description 带实时收录条数 |
| JSON-LD 结构化数据 | ✅ 首页 `WebSite`；列表页 `BreadcrumbList` + `ItemList`（含真实条目）；详情页 `SocialMediaPosting` |
| 服务端取数（预渲染 HTML 内含真实数据） | ✅ 4 个抽奖列表页、爬虫状态页、中奖名人堂、更新日志页 |
| sitemap.xml / robots.txt | ✅ 构建生成，清单与 `src/config/seo_routes.ts` 同源 |

### 两个踩过的坑（改 SEO 相关代码时注意）

1. **`useHead` 的 `script` 不要加 `key`**：它会被 Unhead 当作去重用的 `hid`，导致 JSON-LD 根本进不了 SSR 输出（页面上完全看不到，也没有报错）。
2. **服务端取数必须把数据写回组件状态**：`useAsyncData` 在客户端命中 payload 时**不会执行**回调，
   如果只在回调里填充组件内部状态（ref），SSR 有内容、客户端会渲染成空列表（中奖名人堂踩过）。
   正确做法见 `BiliBaseRanking.vue` 的 `ssr_key` 分支：回调返回完整数据 + 客户端用返回值回填。

## 8. hydration 排查记录（结论 + 方法）

### 已修复的真实问题（都是「服务端与客户端首帧渲染结果不同」）

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| `Hydration text content mismatch: 首页 / Home` | SSR 没有 `navigator` → 语言回落 `zh-CN`；浏览器（英文）首帧按 `navigator.language` → `en` | 首帧两端统一用默认语言 `zh-CN`，挂载后再按浏览器语言切换（`stores/locale.ts` 的 `applyBrowserLocale`） |
| 时间文本不一致 | `toLocaleString()` 不带参数 → 用运行环境默认 locale/时区：构建机 `en-US`、用户浏览器 `zh-CN`，同一时间戳渲染出 `9/21/2026, 4:47:45 PM` 与 `2026/9/21 16:47:45` | 新增 `src/utils/dateFormat.ts`，显式指定 `zh-CN` + `Asia/Shanghai`，SSR 路径上的时间展示统一走它 |
| 列表/排行榜客户端渲染成空 | `nuxt generate` 默认把 payload 抽成 `_payload.json`，HTML 里只留占位 `{"xxx":-1}` → 客户端 hydration 时数据尚未就绪 | `experimental.payloadExtraction = false`（数据随 HTML 下发，顺带少一个请求） |
| 爬虫状态小组件、登录弹层 | 数据/节点只在挂载后出现（`onMounted` 请求、`el-dialog` 依赖 window） | 改 `<ClientOnly>`（**不要**用 `v-if="isMounted"`：它会在 hydrate 期间翻转状态，同样触发 mismatch） |
| 滚动容器高度 | 初值 `window.innerHeight`（SSR 无 window → 0），两端 style 不同 | 初值固定 `0`，挂载后再量真实值 |

### 剩下的一处（仅控制台告警，功能与视觉正常）

```
[Vue warn]: Hydration node mismatch:
- rendered on server: JSHandle@node
- expected on client: Symbol(v-cmt)   ← 客户端期望「注释占位」，服务端渲染了真实节点
```

- **影响**：Nuxt 会自动修正，页面数据（355 / 235 等）、交互、样式全部正常；只是控制台有一条汇总告警。
- **已排除**：`<Suspense>`（已移除，Nuxt 渲染管线自带）、`<transition mode="out-in">` + `<keep-alive>`（临时移除后仍报）、`ClientOnly` 用法、时区/locale。
- **继续定位的方法**（推荐按此顺序）：
  1. 打开详细模式：`nuxt.config.ts` 的 `vite.define` 加 `__VUE_PROD_HYDRATION_MISMATCH_DETAILS__: 'true'`，重新构建后控制台会给出具体节点前后文（定位完记得移除，它会增大产物）；
  2. 若仍不够，用「JS 开关两次加载对比 DOM」：分别以 `javaScriptEnabled: true/false` 打开同一 URL，逐层 diff 结构（注意 `<ClientOnly>` 挂载后的内容是**正常更新**，不算 mismatch）；
  3. 逐个二分全局包裹层（`el-config-provider` / `el-scrollbar` / 全局弹层）——它们都在 `src/App.vue`。
