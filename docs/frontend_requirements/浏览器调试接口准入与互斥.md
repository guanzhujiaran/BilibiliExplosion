# 浏览器调试接口：准入与执行期互斥（前端需求）

> 对应后端：RPA-Browser —— 调试 / 单步执行入口的会话准入口径，以及工作流执行期的互斥约定。
> 关联需求：`docs/frontend_requirements/浏览器启动内存排队.md`（会启动的入口）
> 计划书：`docs/be-message-统一计划书.md` §5.17

## 1. 背景

RPA 浏览器入口分两类：**会启动**（`create` / `pages/*` / `webrtc/offer` / 工作流执行）与**只消费**（调试 / 单步执行）。
后者不承担启动职责，因此在「会话不存在」与「工作流执行中」两种情况下，前端需要给出与启动类入口不同的引导。

## 2. 涉及的调试接口

| 接口 | 说明 |
| --- | --- |
| `POST /browser/control/actions/execute` | 执行单个操作 |
| `POST /browser/control/actions/execute_step` | 单步执行（复合操作调试） |
| `POST /browser/control/workflows/execute_step` | 单步执行工作流步骤 |

以上接口**均不会自动启动浏览器**，也不会进入内存排队。

## 3. 场景一：会话不存在 / 已被闲置回收

**后端返回**：`code = 1007`（`BROWSER_NOT_STARTED`），`msg = "浏览器未启动或已停止"`。

**前端处理**：

1. 提示用户「浏览器未启动」，并**引导点击「启动浏览器」**；
2. 「启动浏览器」走既有 `POST /browser/control/create`；若内存不足会返回 `queued = true` / `2013`，按 `浏览器启动内存排队.md` §5 的排队 UI 处理；
3. **不要自动重试调试请求**——会话不会因此被拉起，只会持续失败。

> 为什么不像 `pages/*` 那样自动启动：单步执行是高频轻量操作，自动启动会让 HTTP 请求阻塞在最长 600s 的内存排队上；且会话被回收通常意味着用户已离开较久，显式重新启动更符合预期。

## 4. 场景二：工作流正在执行

工作流执行期间，**同一会话**的调试类接口会被拒绝，避免与工作流的页面操作相互干扰。

**后端返回**：新增业务码（语义「该浏览器正在执行工作流」），`msg = "浏览器正在执行工作流，请稍后重试"`。

**前端处理**：

1. 提示「浏览器正在执行工作流」，并**禁用调试面板的执行 / 单步按钮**；
2. 可轮询会话状态等待执行结束，结束后恢复按钮；
3. **直播不受影响**：WebRTC 拉流（`offer` / `answer` / `ice-candidate`）在工作流执行期间**正常可用**，不要停流、不要断开拉流连接。

## 5. 与启动类入口的对照

| 场景 | 启动类入口（`create` / `pages/*` / `webrtc/offer`） | 调试类入口 |
| --- | --- | --- |
| 会话不存在 + 内存充足 | 自动启动 | `1007`，引导手动启动 |
| 会话不存在 + 内存不足 | `2013`，进入排队 | `1007`，引导手动启动 |
| 工作流执行中 | 复用会话，正常 | 互斥业务码，提示稍后重试 |
| 工作流执行中 + 直播 | 正常 | **正常**（只读拉流，不受互斥影响） |

## 6. 业务码汇总

| code | 含义 | 前端建议处理 |
| --- | --- | --- |
| `1007` | 浏览器未启动 / 已被回收 | 提示 + 引导点击「启动浏览器」 |
| `2013` | 内存不足，启动请求已进入排队 | 见 `浏览器启动内存排队.md` §5 |
| `2016` | 浏览器正在执行工作流 | 提示「工作流执行中」，不阻断直播 |

## 7. 前端实现落点（本轮已落地）

统一在 `src/components/rpa-browser/useDebugboxExecution.ts` 的 `formatApiError` 内做业务码 → 引导文案映射，
覆盖 `DebugBox.vue` 的全部执行入口（单动作执行、执行选中、分支执行、分支单动作执行）：

- `1007` → 「浏览器未启动或已停止，请先点击「启动浏览器」后再执行」
- `2016` → 「浏览器正在执行工作流（直播不受影响），请等待执行结束后重试」

未命中映射时回退后端 `msg`，再回退调用方传入的兜底文案。
