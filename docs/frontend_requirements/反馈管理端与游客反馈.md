# 报错反馈：游客可提交 + 管理后台 CRUD

## 1. 背景

反馈提交接口（`POST /api/v1/rpa/browser/feedback/submit`）原设计为「先落库、再弱依赖推送服主」，
但只允许登录用户提交，且管理后台没有对应的反馈管理页面 —— 服主只能靠通知里的链接看到「我的反馈」，
无法跨用户处理、补充或清理。

本次补两点：

1. **未登录也允许反馈**：出错了但还没登录是最常见的求助场景。游客提交不记录账号，
   用 `contact`（邮箱 / QQ 等）作为回访渠道；登录用户额外记录 `mid` 与昵称快照 `uname`。
2. **管理后台对全部反馈做 CRUD**：跨提交者（含游客）查看、补录、编辑（含状态 / 处理备注）、删除。

落库仍是主链路，推送仍是弱依赖：**提交成功即落库**，推送失败只告警、不阻塞提交。
推送**只走站外通道**（服主 `NotificationConfig` 决定的邮件 / Webhook 等），不发站内通知。

## 2. 后端接口（已实现）

用户侧（`/api/v1/rpa/browser`，提交允许未登录，列表需登录）：

| 接口 | 说明 |
| --- | --- |
| `POST /feedback/submit` | 提交反馈；可选登录，登录态回填 `mid` / `uname`；游客可传 `contact` |
| `POST /feedback/list` | 查询自己的反馈（分页，需登录） |

管理端（`/api/admin/rpa/feedback`，`require_admin`：root 或 be-message 判定的管理员）：

| 接口 | 说明 |
| --- | --- |
| `POST /list` | 全量反馈分页，支持 `status` / `category` / `mid`（数字字符串）/ `uname` / `keyword` 筛选 |
| `POST /get` | 单条详情（`report_id`） |
| `POST /create` | 手工补录一条反馈 |
| `POST /update` | 更新（未传字段不变；`status` 改为 resolved / ignored 时记录处理人与处理时间） |
| `POST /delete` | 删除（`report_ids` 数组，单条 / 批量共用） |

约定：

- 请求与响应中的 `mid` 一律用**数字字符串**，避免前端大整数精度问题；
- 反馈上下文 `context` 为结构化对象（source / action_id / workflow_id / run_id / browser_id /
  error_message / error_detail / page_url / extra）。

## 3. 前端页面

### 3.1 用户侧：`/app/rpa-browser/feedback`（RpaFeedbackView）

- 路由放开游客访问（`meta.publicAccess = true`），未登录不再跳转社区广场；
- 未登录时页面顶部提示「仍可提交」，并隐藏「我的反馈」列表（改为登录后可见的提示条）；
- 表单新增「联系方式」：**未登录时前端必填**（唯一回访渠道），登录用户选填；
- 提交成功提示区分「已通知服主」与「已落库（服主可在管理后台查看）」；
- 登录态下提交成功后刷新「我的反馈」列表。

### 3.2 管理端：`/app/admin/rpa/feedback`（FeedbackAdmin）

入口：管理后台左侧导航「RPA 管理 → 反馈管理」（管理员 / root 可见，`meta.requiresAdmin`）。

- 筛选：处理状态、分类、关键词（标题 / 描述 / 联系方式）、提交者昵称、提交者 mid；
- 列表列：标题、分类、状态、提交者（昵称 + mid / 未登录游客标签）、联系方式、提交时间、操作；
- 操作：详情（描述 + 结构化上下文 + 处理留痕）、编辑（分类 / 状态 / 标题 / 描述 /
  提交者 mid / 昵称 / 联系方式 / 处理备注）、删除（二次确认）；
- 批量：勾选多条后批量删除，删除后刷新当前页；
- 新增：手工补录（mid 留空即游客）；
- 分页复用 `PaginationBar`；无 `<style>` 块、无内联样式，全部 Tailwind 语义类 + Element Plus 默认尺寸。
