# 运行记录资源结果 & 失败分类展示 · 前端需求

> 后端契约见 `RPA-Browser/docs/通知动作与运行告警计划书.md` §D5 / §D5.1、
> `RPA-Browser/docs/同浏览器工作流排队计划书.md` §4.1。本文件只描述界面行为。

## 1. 背景

工作流运行结论由「资源处理结果」决定，而不是顶层步骤是否跑完。
2026-11-08 run `de801661` 顶层 `18/18` 步骤全绿，但 153 条资源里 18 条处理失败，
运行被判 `failed`；界面只显示「成功 18 / 失败 0 / 共 18」，用户看到自相矛盾的结果。

同时，服务重启导致的 0 步中断会自动整轮重跑，旧记录的 `error_message` 会追加
「已自动重跑 → `<新 run_id>`」，这段留痕必须原样可见，不能截断或改写。

## 2. 字段口径

| 字段 | 语义 |
|---|---|
| `resource_total` | 本次运行处理过的资源总数；0 = 纯步骤型工作流或迁移前的历史记录 |
| `resource_success` | 资源处理成功数（终态） |
| `resource_failed` | 资源处理失败数，**含**可重试软失败 |
| `resource_skipped` | 终态跳过数（如动态 404），不算失败 |
| `resource_soft_failed` | 按 `fail_reason` 判定的可重试软失败数：**只留痕、不改变运行结论** |
| `resource_fatal_failed` | 致命资源失败数：**运行结论的实际判据**（后端阈值默认 1） |

约束：`resource_failed = resource_soft_failed + resource_fatal_failed`；
`resource_total = success + failed + skipped`。
迁移前的历史运行 6 个字段均为 0（迁移不反推历史），界面**不得**据此显示
「0 条资源失败」，统一显示 `-`。

## 3. 界面落点

- 组件：`src/components/rpa-browser/WorkflowRunLogDialog.vue`（运行记录弹窗表格）。
- 工具栏说明补一句资源口径，避免用户把「步骤」与「资源」两列数字混淆。
- 新增「资源结果」列，位于「步骤」之后、「进度」之前：
  - `resource_total === 0`：显示 `-`（`text-color-secondary`）；
  - 有数据时第一行：`成功 S / 失败 F / 跳过 K（共 T）`；成功用 `text-success`、
    失败 `F > 0` 时用 `text-danger`（`F = 0` 用 `text-color-secondary`）、
    跳过与总数用 `text-color-secondary`；
  - 仅当 `resource_failed > 0` 时显示第二行：`可重试 A / 致命 B`，
    可重试数用 `text-warning`、致命数用 `text-danger`，并挂 `el-tooltip` 说明
    「致命失败达到阈值会把整次运行判为失败；可重试失败只留痕，下一轮重新捞起」；
  - 第二行是「步骤全绿却失败」唯一的结构化解释，不可省略。
- 「错误信息」列保持原样展示 `error_message` 全文（含「已自动重跑 → …」留痕），
  不截断、不改写。
- 不新增 `<style>` 块、不使用 `:style`；颜色只用 `theme.css` 语义类
  （`text-success` / `text-danger` / `text-warning` / `text-color-secondary`）。
- 元素命名用 BEM：`workflow-run-log__resource` / `__resource-summary` /
  `__resource-detail`；组件只用 `default` / `large` 尺寸，不出现 `size="small"`。
- 表格 `max-height="56vh"` 与底部 `BiliPagination` 结构不变；新增列不改变
  「操作」列的 `fixed="right"`。

## 4. 数据来源与薄封装

- 列表：`工作流管理Service.listWorkflowRunsApiV1RpaBrowserControlWorkflowsRunsPost`
  的响应已含 6 个字段。后端 `BasePaginationResp` 已由 `SQLModel` 泛型改为
  `pydantic.BaseModel` 泛型，SDK 重新生成后分页 `items` 为
  `Array<WorkflowRunLogItemResponse>`；组件本地 `RunItem` 改为
  `Omit<WorkflowRunLogItemResponse, 'workflow_id' | 'browser_id'>` 派生
  （仅把两个 ID 放宽为 `string` 便于与 props 比较），不再手写字段，
  **不修改生成的 SDK 文件**。
- 详情：`getWorkflowRunApiV1RpaBrowserControlWorkflowsRunsGetPost` 的生成类型
  `WorkflowRunLogDetailResponse` 已含 6 个可选字段；
  `src/api/browser/workflow_run_api.ts` 的 `WorkflowRunProgress`、
  `detailToRunProgress()`、`createPendingRunProgress()` 同步补齐，避免详情映射丢字段。
- 不新增接口调用、不改 SSE 订阅逻辑。

## 5. 验收

1. 打开 `de801661` 所在工作流的运行记录：该历史记录 `resource_total=0`，资源列显示 `-`；
2. 新产生一次带资源记录的运行后，资源列显示四元组，失败数 > 0 时显示「可重试 / 致命」；
3. 步骤全绿但 `status=failed` 的运行，能从资源列直接看出是致命资源失败导致；
4. 服务重启自动重跑后，旧记录的错误信息里能看到「已自动重跑 → 新 run_id」；
5. `npm run type-check` 中本次改动文件无报错（全项目仍有 96 个既有 TS 错误，不在本次范围）；
   `npm run check:route-root` 通过（68 个路由组件）；`npm run test:unit` 158 项通过。
