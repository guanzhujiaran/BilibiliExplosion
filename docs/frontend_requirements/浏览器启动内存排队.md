# 浏览器启动内存排队（前端需求）

> 对应后端：RPA-Browser —— 浏览器启动内存准入 + VIP / 普通双队列。
> 需求来源：RPA 项目启动浏览器时根据服务器内存分配，内存不够则进入排队；
> 队列分两条：**VIP 队列**（大会员）与**普通用户队列**，VIP 优先放行。
>
> 接口统一前缀：`/api/v1/rpa`（下文省略），会话相关接口挂在 `/browser/control` 下。

## 1. 背景与行为约定

服务器内存有限，启动浏览器（Chromium 实例）开销大。后端在启动浏览器前会先看系统可用内存：

| 场景 | 后端行为 | 前端表现 |
| --- | --- | --- |
| 内存充足 | 立即启动，`status = running` | 与现状一致，直接进入浏览器界面 / 拉流 |
| 内存不足 | 进入启动队列排队，后台等待放行后自动启动 | 展示「排队中」状态与排位，轮询排队状态直到 `running` |
| 排队超时 | 排队作废，不会启动 | 提示「服务器繁忙，请稍后重试」，可重试 |
| 排队中被取消 | 用户关闭会话即取消排队，不会启动 | 「关闭」可随时取消排队 |

队列优先级：VIP 队列 **始终优先于** 普通用户队列；同队列内先进先出。
VIP 身份由网关经 `x-bili-vip-status` 请求头透传，前端无需传参。

## 2. 新增接口：排队状态查询

### `POST /browser/control/queue_status`

**唯一**用于拉取排队进度的接口：既可查当前会话的排位，也可查服务器整体繁忙程度。
只读、无副作用、不阻塞；未在排队时也正常返回（`in_queue = false`），全局字段仍可用。

请求：无 body（`mid` 取自请求头，`browser_id` 取自 session / 指纹上下文，与 `/browser/control/status` 一致）。

响应 `data`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `enabled` | `bool` | 是否启用内存准入排队；`false` 表示永不排队 |
| `vip_waiting` | `int` | VIP 队列等待数 |
| `normal_waiting` | `int` | 普通用户队列等待数 |
| `launching` | `int` | 已放行、正在启动的浏览器数 |
| `max_wait_seconds` | `int` | 排队最大等待时长（秒），超过即作废；`0` 表示不限 |
| `max_instances` | `int` | 浏览器实例数上限（运行中+启动中）；`0` 表示仅按内存限制 |
| `memory` | `object` | 系统内存快照，见下表 |
| `browser_memory` | `object` | 浏览器单实例内存**实测**估算（准入额度的来源），见下表 |
| `in_queue` | `bool` | **当前会话**是否在启动队列中（含排队中与已放行启动中） |
| `queue_state` | `string \| null` | `queued`=排队等待；`launching`=已放行、正在启动 |
| `queue_type` | `string \| null` | 所在队列：`vip` / `normal` |
| `queue_position` | `int \| null` | 同队列排位（1 起）；前方还有 `queue_position - 1` 位；`launching` 时为 `null` |
| `queue_waiting_seconds` | `int` | 已排队等待时长（秒） |
| `estimated_wait_seconds` | `int \| null` | 预计还需等待时长（秒）；已放行时为 `0`，未在队列中时为 `null` |
| `estimate_reliable` | `bool` | 估算是否可信：`true`=名额已释放、只受放行冷却限制（较准）；`false`=内存何时释放不可预测，实际可能更久 |

`memory` 子字段：`total_mb` / `available_mb` / `used_mb` / `used_percent` / `required_mb`（启动单浏览器所需最小可用内存）/ `can_launch`。

`browser_memory` 子字段（单实例占用的实测统计，详见 §7）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `enabled` | `bool` | 是否启用实测估算 |
| `sample_count` | `int` | 当前滑窗内的样本数 |
| `window` | `int` | 滑窗长度 |
| `min_samples` | `int` | 生效所需的最小样本数（未达到则用配置基准值） |
| `active_instances` | `int` | 最近一次扫描到的活跃浏览器实例数 |
| `last_sample_mb` | `float \| null` | 最近一次采样的单实例占用 |
| `average_mb` | `float \| null` | 滑窗内平均单实例占用 |
| `peak_mb` | `float \| null` | 单实例占用历史峰值 |
| `reserved_mb` | `int` | **当前准入记账使用的单实例预留额度**（实测自适应结果） |
| `configured_reserved_mb` | `int` | 配置的基准预留额度 |

## 3. 既有接口的变化

### 3.1 创建会话 `POST /browser/control/create`

新增响应字段（`data` 内）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `status` | `string` | 新增取值 `queued`（排队中）；其余仍为 `running` / `failed` |
| `queued` | `bool` | 是否因内存不足进入排队 |
| `queue_type` | `string \| null` | 所在队列：`vip` / `normal` |
| `queue_position` | `int \| null` | 同队列中的排位（1 起） |

```json
{
  "code": 0,
  "data": {
    "success": true,
    "session_id": "123456_789",
    "browser_started": false,
    "status": "queued",
    "created_at": 1767196800,
    "expires_at": null,
    "message": "当前服务器内存不足，已进入VIP队列排队，请稍候",
    "queued": true,
    "queue_type": "vip",
    "queue_position": 2
  }
}
```

> 说明：进入排队后，**创建接口不会阻塞**，真正的启动在后台进行。
> 因此「排队超时」通常不从这个接口返回，而是体现在排队状态查询上：
> `in_queue` 由 `true` 变为 `false` 且会话仍未建立 → 排队已结束但未启动（**超时或被取消**）。
> `code = 2014`（排队超时）只在少见的并发竞态下由本接口同步返回。

### 3.2 会话状态 `POST /browser/control/status`

新增字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `in_launch_queue` | `bool` | 是否处于启动队列（含排队中与已放行启动中） |
| `queue_state` | `string \| null` | `queued` / `launching` |
| `queue_type` | `string \| null` | `vip` / `normal` |
| `queue_position` | `int \| null` | 同队列排位（1 起）；`launching` 时为 `null` |
| `queue_waiting_seconds` | `int` | 已等待时长（秒） |

> ⚠️ 注意：排队中 `session_exists` 仍为 `false`（会话尚未真正建立），
> 判定「正在排队」请用 `in_launch_queue`，**不要**用 `session_exists` / `browser_running`。
> `status` 字段在排队时为 `"queued"`，命中队列前为 `"terminated"`。
>
> 两个接口的分工：`/status` 用于判断**会话是否就绪**（并可顺带读排队字段）；
> `/queue_status` 用于展示**排队进度**（排位、全局繁忙程度、内存水位）。

### 3.3 其他会触发启动的接口

以下接口在「内存不足 + 会话不存在」时**不阻塞**，直接返回业务码 `2013`：

| 接口 | 说明 |
| --- | --- |
| `POST /browser/control/webrtc/offer` | 返回 `code = 2013`，前端应转为排队态并查询 `/browser/control/queue_status` |
| `POST /browser/control/pages/switch` | 同上 |
| `POST /browser/control/pages/close` | 同上 |

`2013` 语义：**当前服务器内存不足，浏览器启动请求已进入排队**，不是失败，前端应提示用户等待并继续轮询状态。

**不触发启动的接口（调试 / 单步执行）**：`/actions/execute`、`/actions/execute_step`、`/workflows/execute_step`
属于「只消费会话」入口——会话不存在或已被闲置回收时**不自动启动**，直接返回 `code = 1007`
（`BROWSER_NOT_STARTED`），前端应引导用户点击「启动浏览器」并按上文流程处理。
另外「工作流执行期间禁止调试（直播不受影响）」的互斥约定，详见
`docs/frontend_requirements/浏览器调试接口准入与互斥.md`（计划书 §5.17）。

### 3.4 关闭会话 `POST /browser/control/close`

排队中关闭：后端取消排队并返回成功，`message = "已取消启动排队"`。
前端「取消排队 / 关闭」按钮可直接调用该接口。

## 4. 业务码

| code | 含义 | 前端建议处理 |
| --- | --- | --- |
| `0` | 成功（含排队中，看 `status` / `queued` / `in_queue`） | 按排队字段分支展示 |
| `2013` | 内存不足，已进入排队 | 提示 + 进入排队轮询 |
| `2014` | 排队超时 | 提示可重试 |
| `2015` | 排队被取消 | 静默 / 提示已取消 |

## 5. 前端交互建议

1. **点击「启动浏览器」**：
   - 响应 `queued = true` → 不进入浏览器界面，改为展示排队卡片：
     - VIP：`正在排队启动（VIP 优先），前面还有 {queue_position - 1} 位`
     - 普通：`服务器繁忙，正在排队启动，前面还有 {queue_position - 1} 位`
   - 响应 `status = running` → 走原有流程（可直接发起 WebRTC offer）。
2. **轮询**：排队期间以 **1~2 秒** 间隔轮询 `POST /browser/control/queue_status` 刷新排位与等待时长；
   同时（或复用原有轮询）请求 `POST /browser/control/status` 判断会话是否就绪：
   - `browser_running = true` → 退出排队态，进入浏览器界面；
   - `in_launch_queue = false` 且 `session_exists = false` → 排队已结束但未启动（**超时或被取消**），
     提示「服务器繁忙，请稍后重试」并结束排队态。
3. **进度展示**：使用 `queue_position` + `queue_waiting_seconds` 展示「前面 N 位 / 已等待 X 秒」，
   并结合 `estimated_wait_seconds` 提示预计时长——措辞随 `estimate_reliable` 区分：

   | `estimate_reliable` | 建议措辞 |
   | --- | --- |
   | `true` | 「预计还需约 {estimated_wait_seconds} 秒」 |
   | `false` | 「预计至少还需 {estimated_wait_seconds} 秒」（内存何时释放不可预测，实际可能更久） |

   `estimated_wait_seconds` 为 `null`（未在队列中）或 `0`（已放行）时不展示预计时长。
   不要基于 `queue_position` 自行换算剩余时间——前端没有实测放行节奏，只有后端有。
   仍可结合 `max_wait_seconds` 提示最长等待上限。
4. **取消**：排队卡片提供「取消排队」按钮 → 调 `POST /browser/control/close`，成功即关闭卡片。
5. **WebRTC offer 返回 2013**：不要直接报错，转为「排队中」状态并轮询上述两个接口。

| `browser_memory_safety_factor` | `1.1` | 实测值的安全系数 |

## 7. 单实例内存占用：实测口径与参考值

**为什么要实测**：单实例占用随指纹参数、页面数量、页面复杂度、是否 WebRTC 拉流变化很大，
写死常量要么浪费内存、要么并发一多就打爆内存。后端因此直接**实测**真实占用并反馈给准入额度。

**口径**：按会话的 `--user-data-dir`（`{user_data_dir}/{mid}/{browser_id}`）聚合 Chromium
进程树（主进程 + renderer/gpu/utility），累加 `/proc/<pid>/smaps_rollup` 的 **PSS**
（共享内存按比例分摊，避免多进程重复计数）。注意 PSS 比 `top` 看到的 RSS 小，
因为 RSS 会把共享库/共享缓存重复计入每个进程。

**本机实测参考**（有头 Chromium + Xvfb，1920x1080，`PSS` 口径）：

| 场景 | 进程数 | 内存占用 |
| --- | --- | --- |
| 空页面（about:blank） | 11 | **≈435MB** |
| 重 DOM 页面（3000 行 + 图片） | 11 | ≈465MB |
| 同一会话再开 4 个 page（共 5 页） | 15 | ≈505MB |
| 会话关闭后 | 0 | 归零，无残留 |

**结论**：
- 单实例基线约 **420~470MB**，每多 1 个 page 约 **+15~20MB**（上限 `browser_max_pages_per_context=10`，
  即最多再加约 150~200MB）；
- 真实业务（B 站页面元素多、含视频解码 + WebRTC 编码）通常高于上表，
  因此基准预留额度取 `768MB` 是偏保守的合理值；
- 实测值超过基准时会**自动上浮**（`reserved_mb = max(基准值, 实测 P90 × 1.1)`，按 16MB 对齐），
  例如实测 1.2GB 时额度自动变为 1.2GB+，从而避免并发启动打爆内存。

**防并发 OOM 的三道约束**（任一不满足即不放行，进入排队）：

1. **系统内存使用率红线**：`used_percent >= browser_launch_max_memory_percent`（默认 90%）。
   Linux 的 `available` 会把可回收 page cache 算进来、偏乐观，单靠它容易触发 OOM Killer。
2. **实测预留记账**：已放行但尚未落地的实例按 `reserved_mb` 预先扣减（已落地实例的真实占用本身就体现在 `available` 里，不重复扣减）。
3. **并发实例数上限**：`运行中 + 启动中 <= browser_max_concurrent_instances`（`0` 表示不启用此项）。

前端可只读 `queue_status` 的 `memory` / `browser_memory` 展示「单实例约 xxxMB、当前 N 个实例、
服务器内存 xx%」，无需自己估算。
