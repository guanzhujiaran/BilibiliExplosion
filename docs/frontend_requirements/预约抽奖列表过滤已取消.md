# 预约抽奖列表首屏过滤已取消

## 背景

`/app/lot-data/bili-data/reserve` 首屏默认只查「未开奖」(`status=unfinished`) 的预约抽奖，
但「预约已取消 / 已失效」并不体现在 `lotdata.status` 上：它由预约关系表
`bili_reserve.t_up_reserve_relation_info.state`（`-100/-300` 失效、`-110/150` 已开奖）
与 `code/etime` 共同判定，仅在响应里表现为 `ReserveInfoResp.available=false`
（前端卡片渲染成「活动已取消」）。

因此首屏仍会混入已取消的预约（本地无预约记录、B 站侧失效等），列表可读性差。

## 需求

1. 首屏（首次加载 / 翻页 / 刷新）默认只展示**预约仍有效**的记录，不再出现「已取消」卡片；
2. 筛选栏提供「仅看有效预约」开关，默认开启，用户可关闭以查看包含已取消记录的历史口径；
3. 过滤发生在**查询参数层**（服务端过滤），保证分页 `total` 与每页条数一致，不做前端截断。

## 方案

### 后端（be-bilibili-crawler）

- `GetReserveLottery` 新增查询参数 `only_available: bool = true`；
  仅当 `status=unfinished` 时生效（已开奖/已取消等状态本身与「预约有效性」不同维度，不叠加过滤）。
- 生效时取预约表中「仍可参与」的 `ids`（`lotteryType=1`、`code=0`、`sid` 非空、`state` 非空且
  不在 `{-100,-300,-110,150}`、`etime >= now`），下推为 `lotdata.business_id IN (...)`，
  与 `query_lottery` 的分页 / count 条件一致。
- 该参数只出现在 `GetReserveLottery` 的 OpenAPI 契约与 `GetLotteryFilterParams`
  的「预约抽奖」元数据中（`filter_widget=switch`、`filter_default=true`），
  不影响官方 / 充电 / 话题 / 第三方动态接口。

### 前端（Vue3FrontEndDemoExercise）

- `useLotteryData.getLotData` 对 `GetReserveLottery` 传 `only_available`
  （`extraFilters` 未给出时兜底 `true`），首屏 SSR 请求与后续翻页口径一致；
- 筛选栏复用现有 `switch` 控件渲染该参数，默认开启；
- SDK 未重新生成前，`LotteryAdvancedQueryParams` 以交叉类型补充该可选字段，
  不修改 `hey-api/` 生成文件。

## 验收

- 默认首屏：`GET /api/v1/lottery_database/bili/GetReserveLottery`（不传 `only_available`）
  返回的 `items` 中不存在 `available=false` 的预约；
- 显式 `only_available=false`：返回结果与改动前一致（含已取消）；
- 筛选 `status=finished` 时 `only_available` 不参与过滤；
- 前端首屏、翻页、应用筛选、刷新四种请求均携带一致口径。
