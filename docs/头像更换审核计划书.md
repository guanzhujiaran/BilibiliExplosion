# 头像更换审核系统计划书

> 状态：草稿
> 模块范围：后端（be-message-service）+ 前端（Vue3FrontEndDemoExercise）
> 关联规则：新增/修改功能需先改计划书再改代码；前端 SDK 变更需暂停等待用户重新生成

---

## 1. 背景与目标

当前「修改头像」在 `POST /api/v1/user/user_info/update` 中**即时生效**：后端下载校验图片 URL 通过后立即写入 `TUserDetail.avatar`，前端随后刷新即看到新头像对外展示。

业务需要改为**先审后发**的流程：

1. 用户提交新头像 → 进入**待审核**状态，不对外展示；
2. 审核**通过** → 新头像写入 `TUserDetail.avatar` 对外公开展示；
3. 审核**驳回** → 保持旧头像不变；
4. **无论审核通过还是驳回**，都通过**系统通知**（`NotifyService.send_to_user`）告知用户审核结果。

审核人：**系统管理员（root）**，在管理后台新增头像审核队列页面进行审核。

## 2. 现有功能盘点（接入前现状）

### 2.1 头像相关后端现状

| 位置 | 说明 |
|------|------|
| `be-message-service/app/api/pptr_user_gateway.py` | `POST /user_info/update` 内校验 `params.avatar` 并即时调用 `PptrUserService.set_user_detail(face=...)` |
| `be-message-service/app/services/avatar_check.py` | `verify_avatar_url()`：图片 URL 下载校验（http/https、≤1MB、1s 内下载完成、Content-Type 为图片） |
| `be-message-service/app/services/pptr_user.py` | `set_user_detail()` 写入 pptr Postgres `TUserDetail`（face→avatar） |
| `bili-common/bili_common/models/pptr_user_gateway.py` | `PptrUserInfoUpdateParams`（含 `avatar` 字段）、`PptrUserInfoUpdateResult` |

`TUserDetail.avatar` 即**对外公开的头像**（用户 nav、动态、评论等场景均回查它展示）。

### 2.2 审核体系参考

已存在成熟的审核范式，本功能对齐复用：

- **动态审核**（`moment_audit.py` / `api/moment_audit.py`）：`TMomentAuditStatus` 状态机 + `TMomentAuditLog` 流水 + 管理端 `RootUser` 守卫 + `GET /list`、`POST /approve`、`POST /reject`。
- **通知**：`NotifyService.send_to_user(mid, title, content, ...)` 系统通知（CUSTOM 定向投放，独立事务弱依赖），评论/私信审核结果通知均走此路径。

### 2.3 前端现状

- `UserCenterDefaultPanel.vue`：`submitAvatar()` 调 `userApi.UpdateUserInfo({ avatar: url })`，成功即关闭弹窗并更新 `navInfo.face`。
- 管理后台：`AdminLayout.vue` 侧边栏 + `src/router/index.ts` 的 `ADMIN_MOMENT_AUDIT`（动态审核）等路由。
- 前端 SDK：`src/api/**/hey-api/` 自动生成，业务封装在 `moment-api.ts` 等薄层。

## 3. 功能设计

### 3.1 数据模型（be-message MySQL 主库新增）

新增表 **`TUserAvatarAudit`**（`app/models/db/avatar_audit.py`，遵循 `TMomentAuditLog` 规范：`T` 前缀、camelCase 列、`TimestampMixin`、`mid` 不建跨库外键）：

| 列 | 类型 | 说明 |
|----|------|------|
| `pk` | BIGINT PK 自增 | 主键 |
| `mid` | BIGINT NOT NULL | 申请更换头像的用户 UID |
| `oldAvatar` | VARCHAR(1024) | 提交时的旧头像 URL（用于回滚/对比） |
| `newAvatar` | VARCHAR(1024) NOT NULL | 申请的新头像 URL |
| `auditStatus` | StrEnum VARCHAR | `pending`（待审核）/ `approved`（通过）/ `rejected`（驳回） |
| `auditOperatorMid` | BIGINT NULL | 审核人 MID |
| `auditReason` | VARCHAR(500) NULL | 驳回原因（驳回时填写）/ 备注 |
| `auditedAt` | datetime NULL | 审核时间 |

索引：`idx_avatar_audit_mid_status`(mid, auditStatus)、`idx_avatar_audit_status_created`(auditStatus, created_at DESC)。

新增枚举（`app/models/enums.py`）：
```python
class AvatarAuditStatusEnum(StrEnum):
    PENDING = "pending"
    APPROVED = "approved"
    REJECTED = "rejected"
```

**关键语义**：`TUserDetail.avatar` 只存**审核通过后**的头像（对外公开）；`TUserAvatarAudit.newAvatar` 存待审核/已处理的申请，与公开头像解耦。

### 3.2 后端接口改造

#### (1) 修改 `POST /api/v1/user/user_info/update`

`avatar` 字段语义从「即时更新」改为「**提交更换申请**」：

- 仅当 `params.avatar` 非空时进入头像更换流程（其余字段 uname/sign/sex/birthday 仍即时更新，不受影响）。
- 头像更换流程：
  1. 仍复用 `verify_avatar_url()` 做基础合法性校验（http/https、≤1MB、图片类型），校验失败返回 422；
  2. 在 `TUserAvatarAudit` 插入一条 `auditStatus=pending` 记录（`oldAvatar` = 当前 `TUserDetail.avatar`，`newAvatar` = `params.avatar`）；
  3. **不写** `TUserDetail.avatar`，公开头像保持不变；
  4. 用户侧此时可见「待审核」状态。

- 校验逻辑（`PptrUserInfoUpdateParams.avatar`）：
  - 有「进行中（pending）的申请」时，是否允许再次提交？→ **允许覆盖**：新申请插入后，旧 pending 记录置为 `rejected`（原因「已重新提交新申请」）或保留多条均可。设计取**后提交覆盖前 pending**：置旧 pending 为 `rejected`（reason 固定），保证同一时刻至多一条 pending。见 §7 风险说明。

- `PptrUserInfoUpdateResult` 需扩展，新增 `avatarAudit` 信息：
```json
{
  "uid": "...",
  "updated": true,
  "uname_recorded": false,
  "avatar_status": "pending"        // 本次 avatar 字段处理结果：pending（提交审核）/ 不传 avatar 时无此字段或 "none"
}
```

#### (2) 新增管理端审核 API（`RootUser` 守卫）

路由文件新增 `be-message-service/app/api/avatar_audit.py`，`router = APIRouter(prefix="/api/v1/user/avatar/audit", tags=["avatar-audit"])`，在 `main.py` 注册：

- `GET /list`：待审核列表（`auditStatus=pending`，按 `created_at` 倒序分页）。
  - 响应项含：`pk`、`mid`、`oldAvatar`、`newAvatar`、`createdAt`；作者昵称/旧头像经 `PptrUserService.get_many` 只读回查。
- `POST /approve`：body `{ pk, remark? }`。
  - `auditStatus → approved`，写 `auditOperatorMid` / `auditedAt`；
  - **同一事务**内调用 `PptrUserService.set_user_detail(uid=mid, face=newAvatar)` 把新头像写入 `TUserDetail.avatar`（对外公开）；
  - 成功后**系统通知用户**（通过）；返回更新后的记录。
- `POST /reject`：body `{ pk, reason, remark? }`。
  - `auditStatus → rejected`，写 `auditOperatorMid` / `auditedAt` / `auditReason`；
  - **不改** `TUserDetail.avatar`（保持旧头像）；
  - 成功后**系统通知用户**（驳回 + 原因）。

权限守卫：与 `moment_audit.py` 一致，接口入参 `user: RootUser`。

### 3.3 审核结果通知

通过 `NotifyService.send_to_user` 定向通知（弱依赖，失败不影响审核主流程）：

- **通过**：`title="头像审核通过"`，`content` 含「您的新头像已审核通过并公开显示」。
- **驳回**：`title="头像审核未通过"`，`content` 含「您提交的头像未通过审核，已保留原头像」+ 驳回原因。

`level` 建议：驳回用 `NotifyLevelEnum.IMPORTANT`（与评论驳回一致），通过用 `NORMAL`。

### 3.4 前端改造

#### (1) 用户中心（`UserCenterDefaultPanel.vue`）

- `submitAvatar()` 调用 `UpdateUserInfo({ avatar })` 后，按返回的 `avatar_status` 处理：
  - `pending` → 关闭输入弹窗，展示「头像更换申请已提交，审核通过后生效」的成功提示（非直接改 `navInfo.face`）。
- 增加「待审核」提示：若当前有 `pending` 的头像审核记录，在头像区域展示待审核徽标（不展示新头像，仍显示旧头像）。
- 需新增接口查询「我的头像审核状态」→ 见 3.5 额外接口。

#### (2) 管理后台（新增头像审核页面）

- `AdminLayout.vue` 侧边栏「动态管理端」组（或新增「用户管理端」组）增加「头像审核」入口（icon 复用 `Picture`/`Checked`），仅 `isRpaAdmin`（root）可见。
- 新增页面 `src/views/admin/AvatarAuditListView.vue`（参考 `MomentAuditListView.vue` 写法，遵循 Vue + Tailwind + Element Plus 规范）：
  - 待审核列表：展示作者、新旧头像缩略图、提交时间；
  - 操作：通过 / 驳回（驳回弹窗输入原因）；
  - 可选：已处理记录 tab / 流水。

### 3.5 额外接口

用户侧新增「我的头像审核状态」查询，便于前端展示待审核徽标与结果：

- `GET /api/v1/user/avatar/audit/mine`（`CurrentUser`，仅本人）：
  - 返回最近一条审核记录：`{ pk, newAvatar, auditStatus, auditReason, createdAt, auditedAt }`；
  - 前端据此在头像区域渲染「待审核/已驳回」状态。

> 若为避免额外接口，也可在 `GET /user_info` 响应中扩展 `avatar_audit` 字段（返回最近一条审核状态）。计划取**独立接口**，职责更清晰、改动更收敛。

## 4. 接口详细约定

### 4.1 用户提交头像更换（修改现有接口）

```
POST /api/v1/user/user_info/update
Authorization: Bearer <JWT>
{ "avatar": "https://example.com/new.png" }
```

响应（`StandardResponse`，成功 `code=0`）：
```json
{
  "code": 0,
  "msg": "更新成功",
  "data": {
    "uid": "123",
    "updated": true,
    "uname_recorded": false,
    "avatar_status": "pending"
  }
}
```

- `avatar_status=pending`：头像已提交审核，未立即生效。
- 未传 `avatar` 时无该字段（或 `"none"`）。

### 4.2 我的头像审核状态

```
GET /api/v1/user/avatar/audit/mine
```
```json
{
  "code": 0,
  "msg": "",
  "data": {
    "pk": 1,
    "newAvatar": "https://example.com/new.png",
    "oldAvatar": "https://example.com/old.png",
    "auditStatus": "pending",
    "auditReason": null,
    "createdAt": "2026-08-16T10:00:00",
    "auditedAt": null
  }
}
```

无记录时 `data=null`。

### 4.3 管理端审核

```
GET  /api/v1/user/avatar/audit/list?pageNum=1&pageSize=20
POST /api/v1/user/avatar/audit/approve   { "pk": 1, "remark": "ok" }
POST /api/v1/user/avatar/audit/reject    { "pk": 1, "reason": "图片不清晰", "remark": "" }
```

列表项：`{ pk, mid, authorName, oldAvatar, newAvatar, createdAt }`。

### 4.4 错误码

沿用 `bili_common.models.ResponseCode`：`0` 成功；`404` 记录不存在；`422` 头像校验失败；`401` 未登录；`403` 非 root 访问管理端接口。

## 6. 验收标准

- 用户提交新头像后，公开头像**保持不变**，并提示「待审核」。
- 管理后台头像审核列表能看到待审核申请，可查看新旧头像缩略图。
- 审核通过：用户公开头像更新为新头像，用户收到「头像审核通过」系统通知。
- 审核驳回：公开头像保持旧头像，用户收到「头像审核未通过」系统通知并含驳回原因。
- 仅 root 可访问管理端审核接口；`mine` 仅本人可查。
- 前端遵循 Vue + Tailwind + Element Plus 规范，无 `<style>` 块。

## 7. 风险与注意事项

- **并发/重复提交**：同一时刻至多一条 `pending` 记录（新提交覆盖旧 pending，旧 pending 置为 rejected）。需在服务层做「查 pending → 置旧为 rejected → 插入新记录」的原子处理（同事务），必要时加 `(mid, auditStatus)` 部分唯一约束（MySQL 唯一索引允许多个 `rejected`，仅限制 `pending`，可用生成列/应用层保证）。
- **审核通过写入公开头像的时序**：`approve` 中「更新申请状态」与「写 `TUserDetail.avatar`」必须**同一事务**，避免状态已通过但头像未生效（或反之）的中间态。
- **通知弱依赖**：通知走 `NotifyService.send_to_user` 独立事务，失败只记日志，不回滚审核。
- **旧 pending 覆盖**会导致用户已提交的申请被悄悄作废，需在通知中明确提示（覆盖时也可不通知，仅记录原因字段，供管理端追溯）。
- **SDK 依赖**：前端必须等 SDK 重新生成后才能接入 `avatar_status` 与新增审核接口，期间不得提交会报错的实现。
